# streammux 追加・変更要求設計書 v0.1

## 1. 目的

本書は、AriadneMultiplexer から `github.com/aruzen/streammux` を利用するために、streammux 側へ追加・変更する機能と、その責務境界を定義する。

最小構成だけを目的とせず、以下を後から破壊的に再設計しなくてよい構造を最初に確立する。

- 1 本の full-duplex connection 上での複数 protocol / 複数 PTY の多重化
- connection と独立した PTY lifetime
- attach / detach / reattach
- frontend 不在時を含む継続的な PTY output drain
- 上限付き history と順序保証された replay
- slow consumer、backpressure、stream 間公平性
- Unix / Windows backend の差し替え
- application 固有 protocol との共存

本書では `MUST` を必須、`SHOULD` を原則採用、`MAY` を任意拡張とする。

---

## 2. Scope

### 2.1 streammux の責務

streammux は以下を担当する。

- opaque payload を持つ frame codec
- request / response / event の通信モデル
- 一つの connection に対する protocol dispatcher
- CorrelationID の採番と pending request 管理
- 複数 PTY process の生成、入出力、resize、終了待機
- connection 非依存の PTY session 管理
- PTY session への attach / detach
- PTY output の buffering、history、subscriber 配信
- connection および subscriber 単位の backpressure 制御
- platform 非依存 interface と Unix backend
- 将来の Windows backend を追加できる境界

### 2.2 streammux の非責務

以下は AriadneMultiplexer または利用 application が担当する。

- Workspace / Window / Pane
- stash という UI 操作
- Label / Attention
- coding agent の識別と Plugin 管理
- application の認可 policy
- application domain event
- terminal screen model と VT interpretation
- daemon restart を跨ぐ process persistence

streammux は Ariadne の domain type を import してはならない。

## 3. 現状の問題

現在の framing core、`Conn`、`pty.Factory`、`pty.Process`、Unix PTY backend は基本構造として利用できる。

一方、現在の `pty.Mux` / `pty.Bridge` には以下の問題がある。

1. `Mux.Run` の終了が全 PTY の終了につながり、connection と PTY lifetime が結合している。
2. `Bridge` が一つの sender に固定され、detach / reattach できない。
3. connection への同期送信が block すると PTY output の read も停止する。
4. frontend 不在時の継続 read と history 保持がない。
5. custom protocol は単一の `Unhandled` callback に委ねられ、複数 protocol の合成が難しい。
6. request の CorrelationID 採番、response 待機、timeout 管理を各 application が再実装する必要がある。
7. queue が frame 数基準であり、memory 使用量と stream 間公平性を制御できない。
8. Unix process の終了が process tree 全体の終了を保証しない。

既存 API をそのまま拡張して責務を増やすのではなく、後述する `Peer`、`pty.Manager`、`pty.Protocol` に分離する。

## 4. Target Architecture

```text
Application daemon lifetime
│
├─ streammux.Peer
│    ├─ one streammux.Conn
│    ├─ request / response correlation
│    ├─ protocol registry / dispatcher
│    └─ outbound scheduler
│
└─ pty.Manager
     ├─ Session #1 ─ output pump ─ history ─ attachments
     ├─ Session #2 ─ output pump ─ history ─ attachments
     └─ Session #N ─ output pump ─ history ─ attachments

Connection lifetime
└─ pty.Protocol
     ├─ Peer に PTY message handler を登録
     ├─ connection と Session attachment を関連付け
     └─ connection 終了時は attachment のみ解除
```

依存方向は次とする。

```text
streammux core
    ↑
pty abstraction
    ↑
pty.Manager / pty.Protocol
    ↑
platform backend
```

`pty.Manager` は `streammux.Conn` を所有しない。`pty.Protocol` は PTY process を所有しない。

---

## 5. 不変条件

以下は全実装で維持する。

1. connection の切断だけでは PTY session を終了しない。
2. Manager の終了時には所有する全 PTY session を終了し、`Wait` 完了まで回収する。
3. PTY output は attachment の有無にかかわらず読み続ける。
4. 一つの slow attachment が PTY、他 attachment、他 stream、Manager を block しない。
5. PTY input / output bytes の内容を変換しない。
6. 同一 Session の output 順序を保持する。
7. history replay と live output の間に欠落や順序逆転を発生させない。
8. Core frame reader は connection ごとに一つだけ存在する。
9. application 固有 message と PTY message を同じ Peer に安全に登録できる。
10. OS 固有型を `pty.Manager`、protocol、applicationへ露出させない。

## 6. Core Communication Layer

### 6.1 Frame format

現在の固定 header を維持する。

```text
PayloadLength uint32
Version       uint16
MessageType   uint16
Flags         uint32
CorrelationID uint64
StreamID      uint64
Payload       opaque bytes
```

PTY input / output は Payload に raw bytes を格納する。Control payload の encoding は protocol ごとに決定し、framing core は関知しない。

decoder は payload allocation 前に version、flag、message type、length 上限を検証しなければならない。

### 6.2 Peer

`Peer` を `Conn` の上位層として追加する。

```go
type PeerConfig struct {
    OutboundQueueBytes  int
    PerStreamQueueBytes int
    MaxActiveStreams    int
    ControlWeight       int
    InteractiveWeight   int
    BulkWeight          int
}

type Peer interface {
    Register(MessageType, Handler) error
    Call(context.Context, Frame) (Frame, error)
    Emit(context.Context, Frame) error
    Serve(context.Context) error
    Close() error
    Done() <-chan struct{}
    Err() error
}

func DefaultPeerConfig() PeerConfig
```

実際の Go API は interface ではなく concrete type でもよいが、以下の semantics を満たすこと。

- `Serve` だけが `Conn.ReadFrame` を呼ぶ。
- request は MessageType handler へ dispatch し、同じ CorrelationID を持つ response を返す。
- `Call` は非 0 の CorrelationID を自動採番し、response、context cancellation、connection close のいずれかを待つ。
- CorrelationID は一つの connection 内で pending request と重複させない。
- event は CorrelationID 0 とする。
- response に対応する pending request がない場合は protocol error とする。
- 同じ MessageType の重複登録を拒否する。
- handler の panic は connection process 全体を crash させず、protocol error として処理する。
- connection 終了時は全 pending request を共通の close error で完了させる。
- 既定weightはcontrol 8、interactive 4、bulk 1とする。

### 6.3 Dispatch concurrency

dispatch は次の順序を保証する。

- 同じ StreamID に属する frame は受信順に処理する。
- 異なる StreamID は並行処理してよい。
- StreamID 0 の connection-global control は順序を保持する。
- handler 実行中も sole read loop は次の frame を読み取れる構造とする。
- stream ごとの未処理 queue は byte 上限を持つ。
- queue 上限超過時の動作は protocol error と connection close とし、無制限 goroutine 生成は禁止する。

### 6.4 Message type registry

`Peer.Register` を唯一の message routing 登録点とする。

PTY protocol の MessageType は `pty.MessageTypes` により利用 application が割り当てる。すべて非 0 かつ重複なしでなければならない。

Peer は application message を同時登録できる。従来の単一 `Unhandled` callback は互換用 API とし、新規実装では使用しない。

### 6.5 Outbound scheduling

一つの connection 上で複数 stream を扱うため、送信 queue は次を満たす。

- queue 容量を frame 数と合計 payload bytes の両方で制限する。
- control response、interactive input、bulk output の traffic class を持つ。
- control responseを優先するが、特定 class を永久に starvation させない。
- 同じ StreamID 内の順序を変えない。
- PTY output frame は既定 32 KiB 以下に分割し、一つの大きな output がconnectionを長時間占有しない。
- queue 待機は context cancellation で解除できる。
- payload ownership transfer API の契約を維持する。

既定 scheduling は control優先の weighted round-robin とし、weight は設定可能にする。

## 7. PTY Domain Model

### 7.1 Manager

`pty.Manager` は複数の Session とその process を所有する。

```go
type ManagerConfig struct {
    MaxSessions              int
    HistoryBytes             int
    MaxTotalHistoryBytes     int64
    ReadBufferBytes          int
    AttachmentQueueBytes     int
    ObserverQueueBytes       int
    MaxObservers             int
    MaxAttachmentsPerSession int
    GracefulKillTimeout      time.Duration
}

type Manager struct {
    // implementation private
}

func DefaultManagerConfig() ManagerConfig
func NewManager(context.Context, Factory, ManagerConfig) (*Manager, error)
func (m *Manager) Open(context.Context, ProcessSpec) (*Session, error)
func (m *Manager) Get(StreamID) (*Session, bool)
func (m *Manager) List() []SessionInfo
func (m *Manager) Kill(context.Context, StreamID) error
func (m *Manager) Close() error
```

```go
type SessionState string

type SessionInfo struct {
    ID           StreamID
    State        SessionState
    Size         Size
    StartedAt    time.Time
    LastSequence uint64
    Exit         *ExitStatus
}
```

SessionInfo は process 内部handleを含めず、wire codecへ安全に渡せるsnapshotとする。ProcessSpec、特にenvironmentを一覧応答で無条件に公開しない。

- Manager context は daemon / owning application lifetime を表す。
- `Open` に渡す操作 context は起動処理だけを制御し、起動後の Session lifetime には使用しない。
- StreamID は Manager が採番する非 0 の値とする。
- StreamID は Manager lifetime 中に再利用しない。
- ID 空間を使い切った場合は新規 Session を拒否する。
- `Close` は冪等であり、新規 Open を停止してから全 Session を終了する。
- `List` は安定した snapshot を返し、内部可変 storage を共有しない。
- constructor は `DefaultManagerConfig()` が返す値を基準とし、各 field を検証する。HistoryBytes の 0 だけは明示的な history 無効として扱い、未指定値との曖昧な自動補完を行わない。
- Session数、observer数、Session単位history、Manager全体historyの上限を同時に適用する。Manager全体のhistory上限に達した場合は、全Sessionを通した最古chunkから削除する。

### 7.2 Session state

Session は以下の状態を持つ。

```text
STARTING
   ├─ start success → RUNNING
   └─ start failure → FAILED

RUNNING
   ├─ process exit  → EXITED
   ├─ Kill          → STOPPING
   └─ Manager close → STOPPING

STOPPING
   └─ process Wait完了 → EXITED
```

`FAILED` と `EXITED` は terminal state とする。

Manager の公開一覧には原則として RUNNING / STOPPING の Session を保持する。EXITED Session の結果は Exit event 配信完了まで保持し、その後削除する。長期的な終了履歴は application の責務とする。

### 7.3 Session API

```go
type Session interface {
    ID() StreamID
    Info() SessionInfo
    Input(context.Context, []byte) error
    Resize(context.Context, Size) error
    Attach(context.Context, AttachOptions, OutputSink) (Attachment, error)
    Kill(context.Context) error
    Wait(context.Context) (ExitStatus, error)
}
```

- `Input` は payload 全体を書き込むか error を返す。
- concurrent Input は Session 内で直列化する。
- Resize は最後に成功した size を SessionInfo に保持する。
- Kill、Wait、Attachment.Close は冪等に扱えること。
- Session API は `io.Reader` を外部へ直接公開しない。PTY output を読む goroutine は一つに限定する。

### 7.4 Process abstraction

`Process` は以下の意味を明示する。

```go
type Factory interface {
    Start(context.Context, ProcessSpec) (Process, error)
}

type Process interface {
    Output() io.Reader
    Input() io.Writer
    Resize(Size) error
    Terminate() error
    Kill() error
    Wait() (ExitStatus, error)
    Close() error
}
```

実際の署名は互換性を考慮して段階移行してよいが、exit code を optional type assertion で取得する構造は廃止し、全 backend が型付き ExitStatus を返す。

Factory.Startへ渡すcontextは起動操作のcancelにだけ使用し、起動後のprocess lifetimeへ結び付けない。Unix backendはfrontendやrequest由来contextを`exec.CommandContext`へそのまま渡してはならない。cancelと起動成功が競合した場合、FactoryまたはManagerが生成済みprocessを確実に回収してからcancel errorを返す。

```go
type ExitReason string

const (
    ExitReasonExited      ExitReason = "exited"
    ExitReasonKilled      ExitReason = "killed"
    ExitReasonSignaled    ExitReason = "signaled"
    ExitReasonStartFailed ExitReason = "start_failed"
    ExitReasonIOFailure   ExitReason = "io_failure"
)

type ExitStatus struct {
    Reason ExitReason
    Code   int
    Signal string
    Error  string
}
```

Signal は利用可能な platform のみ設定し、OS 固有数値型は公開しない。

Terminate はgraceful終了要求、Killは即時強制終了とする。対応platformでgraceful終了を表現できない場合、Terminateは明示的なunsupported errorを返し、ManagerがKillへ移行する。

Process.CloseはPTY handle等のresource解放であり、Killの別名にしない。Session cleanupがTerminate / Kill、Wait、Closeを規定順序で実行する。

### 7.5 ProcessSpec

ProcessSpecには初回描画前のresize競合を避けるため、起動時terminal sizeを追加する。

```go
type ProcessSpec struct {
    Command     string
    Args        []string
    Env         []string
    Dir         string
    InitialSize Size
}
```

- Commandは必須とする。
- InitialSizeのcolumns / rowsは正数とし、backend固有上限はStart時に検証する。
- Envがnilの場合はdaemon environmentを継承し、non-nilの空sliceは空environmentを意味する。
- Args、Env、Dirは呼出し後に変更されても影響しないようcopyする。
- NUL等、OS APIへ安全に渡せない値をbackend呼出し前に拒否する。
- Unix backendはPTY生成時にInitialSizeを適用し、childが最初に観測するsizeを保証する。

## 8. Output Pump、History、Observer

### 8.1 Output pump

各 Session は起動成功直後に一つの output pump を開始する。

```text
PTY output
    ↓ single reader
Session output pump
    ├─ bounded history
    ├─ Manager observer
    └─ attachment #1..N
```

output pump は attachment が 0 件でも停止しない。PTY EOF または致命的 read error まで読み続ける。

read buffer を再利用する場合、history、observer、attachmentへ渡す前に所有権を移譲できる immutable chunk を生成する。受信側が次の read により内容を破壊されてはならない。

各 output chunk には Session 内で単調増加する非 0 の sequence 番号を割り当てる。sequence は同じ Session 内で再利用しない。

Protocolは一つのOutputEventを一つのOutput frameへ対応させ、結合や再分割を行わない。ReadBufferBytesは接続で許容される最大payload以下に制限し、sequenceとwire上のframe境界を一致させる。

### 8.2 History

history は chunk queue または ring buffer とし、保持量を byte 数で制限する。

- 既定値は 16 MiB / Session。
- 0 は history 無効を表す。
- 上限超過時は古い完全 chunk から削除する。
- 一つの chunk が上限より大きい場合は末尾側だけを保持してよい。
- VT screen snapshotとしての完全性は保証しない。
- history はSession終了時に解放する。
- history は chunk の sequence 番号を保持する。

history は stash 中だけでなく、Session lifetime 全体の直近 output を保持する。これによりconnection切断後も同じattach処理で復帰できる。

### 8.3 Observer

Manager は application 内部観測用 subscription を提供する。

```go
type EventKind string

const (
    EventOpened EventKind = "opened"
    EventOutput EventKind = "output"
    EventExited EventKind = "exited"
)

type Subscription interface {
    Events() <-chan Event
    Close() error
    Done() <-chan struct{}
    Err() error
}
```

- observer は connection attachment と別管理とする。
- observer queue も byte 上限を持つ。
- slow observer は PTY output pump を block しない。
- overflow時は当該subscriptionをerror付きでcloseする。
- Output event のbytesはsubscriberが保持できる所有権を持つ。

Ariadne はこの Event を Core Event / Plugin event へ変換する。

## 9. Attachment

### 9.1 Model

Attachment は Session と OutputSink の一時的な関連である。

```go
type ReplayMode string

const (
    ReplayNone    ReplayMode = "none"
    ReplayHistory ReplayMode = "history"
)

type AttachOptions struct {
    Replay      ReplayMode
    ResumeAfter uint64
}

type OutputEvent struct {
    Sequence uint64
    Data     []byte
}

type AttachResult struct {
    ReplayFirst uint64
    ReplayLast  uint64
    NextLive    uint64
    Truncated   bool
}

type OutputSink interface {
    Send(context.Context, OutputEvent) error
}

type Attachment interface {
    ID() uint64
    Close() error
    Done() <-chan struct{}
    Err() error
}
```

Manager内部は複数Attachmentを扱える構造とする。Ariadne初期設定では `MaxAttachmentsPerSession = 1` とし、将来値を増やしてもSession設計を変更しない。

### 9.2 Attach ordering

ReplayHistory の attach は次の順序を保証する。

```text
Attach accepted
    ↓
ReplayBegin
    ↓
retained history in original order
    ↓
ReplayEnd
    ↓
live output
```

attach準備中に発生したlive outputは一時queueへ積み、ReplayEnd後に送信する。history snapshot取得とlive queue登録はSession内でatomicに行う。

`ResumeAfter` が非 0 の場合は、その sequence より後の保持 chunk だけを replay する。要求位置が既に history から失われている場合は、ReplayBegin metadata の `truncated` を true にし、現在保持している最古 chunk から replay する。未来の sequence を指定した場合は request error とする。

wire 上の Output payload は raw bytes のままとする。ReplayBegin は最初と最後の sequence を通知し、client は同一 StreamID の Output frame ごとに sequence を進める。これにより payload へ独自 header を追加せず、再接続時の継続位置を指定できる。

Replay対象がない場合はReplayFirst / ReplayLastを0とする。ReplayNoneの場合もAttach responseのNextLiveで、最初に届くlive Outputのsequenceを確定できるようにする。ProtocolはAttach responseを送信queueへ登録した後にAttachmentをactivateし、同一StreamIDの順序保証によりOutputがresponseを追い越さないようにする。

### 9.3 Detach

以下の場合にAttachmentだけを終了する。

- 明示的なDetach
- Peer / connection終了
- attachment context終了
- OutputSink送信失敗
- attachment queue overflow

いずれの場合もSession、PTY process、history、observerは継続する。

wire protocol用AttachmentでOutputSink送信失敗またはqueue overflowが発生した場合、Protocolはbest-effortでerrorを通知した後、そのPeer connectionを閉じる。同じconnection上の全Attachmentはdetachされるが、対応Sessionは継続する。

Session終了時には全Attachmentを終了し、Exit event送信を試行してからqueueを閉じる。

## 10. PTY Wire Protocol

### 10.1 Protocol composition

`pty.Protocol` は `Peer` にhandlerを登録するcomponentとする。connectionのread loopやManager lifetimeを所有しない。

```go
type Protocol struct {
    // Manager、Peer、MessageTypes、connection-local attachments
}

func RegisterProtocol(*Peer, *Manager, ProtocolConfig) (*Protocol, error)
func (p *Protocol) Close() error
```

`Protocol.Close` はそのPeerに属するAttachmentを解除するだけであり、Manager.CloseやSession.Killを呼ばない。

### 10.2 Message set

`MessageTypes` は少なくとも以下を持つ。

| Message | Flags | StreamID | Payload |
| --- | --- | --- | --- |
| Open | request / response | 0 | request: ProcessSpec、response: SessionInfo |
| List | request / response | 0 | cursor / SessionInfo page |
| Inspect | request / response | Session ID | response: SessionInfo |
| Attach | request / response | Session ID | AttachOptions / AttachResult |
| Detach | request / response | Session ID | empty / result |
| Input | event | Session ID | raw bytes |
| Output | event | Session ID | raw bytes |
| Resize | request / response | Session ID | Size / result |
| Kill | request / response | Session ID | empty / result |
| Exit | event | Session ID | ExitStatus |
| ReplayBegin | event | Session ID | replay metadata |
| ReplayEnd | event | Session ID | empty |

すべてのPTY MessageTypeは非0かつ互いに異なる値とする。具体値はapplicationが設定し、Peerの重複登録検査を通す。

Listはcursor-based paginationとし、1 responseがMaxFrameBytesを超えないよう件数上限を適用する。cursorはManager snapshot世代と位置を表すopaque valueとし、古い世代または不正なcursorを明示的なerrorとして返す。

未releaseの`Close` messageは採用せず、新規protocolでは`Kill`と`Detach`を明確に分離する。既に内部利用がある場合だけ、利用側の移行期間中にPTY終了を意味するlegacy aliasとして提供してよい。

### 10.3 Payload encoding

- Input / Output はraw bytesとする。
- Sizeはnetwork byte orderの固定長表現を維持する。
- ProcessSpec、SessionInfo、ExitStatus、Replay metadata、errorはversion fieldを持つ構造化payloadとする。
- 構造化payloadの標準codecはJSONを維持してよい。
- decoderはunknown fieldを許容し、必須field欠落と不正値を拒否する。
- error文字列だけで分岐させず、安定したErrorCodeを持たせる。

### 10.4 Error model

```go
type ErrorCode string

const (
    CodeInvalidRequest      ErrorCode = "invalid_request"
    CodeSessionNotFound     ErrorCode = "session_not_found"
    CodeSessionExists       ErrorCode = "session_exists"
    CodeAlreadyAttached     ErrorCode = "already_attached"
    CodeAttachmentLimit     ErrorCode = "attachment_limit"
    CodeManagerClosed       ErrorCode = "manager_closed"
    CodeUnsupportedVersion  ErrorCode = "unsupported_version"
    CodeQueueOverflow       ErrorCode = "queue_overflow"
    CodeBackendFailure      ErrorCode = "backend_failure"
)
```

remote error payloadはErrorCode、human-readable message、任意detailを持つ。Go clientは`RemoteError`へdecodeし、`errors.Is`またはcode比較ができること。

protocol違反、frame破損、未登録MessageTypeはconnectionを終了する。Session単位の操作errorはresponseとして返し、connectionは維持する。

## 11. BackpressureとFailure Isolation

### 11.1 Queue boundaries

以下を独立したbounded queueとする。

- Peer outbound queue
- StreamIDごとのdispatch queue
- Attachmentごとのoutput queue
- Observer subscriptionごとのevent queue

全queueは少なくともbyte上限を持つ。設定値が不正な場合はconstructorで拒否し、暗黙にunboundedへ変更しない。

### 11.2 Overflow policy

| 対象 | Overflow時の動作 |
| --- | --- |
| Attachment output | Attachmentを切断。Sessionは継続 |
| Observer | Subscriptionを切断。Sessionは継続 |
| Peer outbound control | 呼出元へerror。必要ならconnection終了 |
| Per-stream inbound | protocol errorとしてconnection終了 |
| History | 古いchunkを削除 |

PTY outputを黙ってdropし、attachmentを生存させ続けてはならない。drop後のterminal表示が正常に見えてしまうことを避けるためである。

### 11.3 Fairness

複数Sessionの大量outputが、他Sessionのinteractive trafficとcontrol responseを恒常的に妨げてはならない。

送信schedulerはStreamID単位のround-robinとtraffic class優先度を組み合わせる。同一streamのframe順序は維持する。

## 12. Process LifetimeとCleanup

### 12.1 Ownership

```text
Manager owns Session
Session owns Process and PTY handle
Protocol owns Attachment only
Peer owns Connection only
```

connection close、protocol close、detachはProcess.Closeを呼ばない。

Manager.Close、Session.Kill、自然終了時のcleanupだけがProcess回収を行う。

Manager.Closeは次の順で実行する。

1. Managerをclosing状態にして新規Open / Attachを拒否する。
2. 全SessionへTerminateを並行送信する。
3. 全Sessionで共通のgrace periodまで待つ。
4. 残存SessionへKillを並行送信する。
5. 全ProcessのWaitとPTY handleのCloseを完了する。
6. output pump、observer、attachmentのgoroutine終了をjoinして返る。

Session.Killは強制終了、Wait、resource cleanupまで完了してから成功を返す。呼出しcontextが途中でcancelされても、開始済みcleanupはManager管理下で継続する。

Manager lockまたはSession lockを保持したまま、Process I/O、OutputSink、observer callback、Peer Send等の外部処理を呼んではならない。lock順序を必要とする場合はManagerからSessionの順に固定し、逆順取得を禁止する。

### 12.2 Unix backend

Unix backendは次を満たす。

- PTY processを独立したsession/process groupとして起動する。
- Killはprocess leaderだけでなく所有process groupを終了する。
- graceful termination用signalと強制killの二段階を設定可能にする。
- 強制kill timeout後も必ずWaitを呼び、zombieを残さない。
- PTY master closeとWaitの順序を定義し、macOS/LinuxのEIOをEOFへ正規化する。
- PID再利用による別process groupへの誤signalを避ける。
- Kill、Close、Waitの同時呼出しをrace-freeかつ冪等にする。

Manager既定値はgrace period 2秒、その後強制killとする。applicationは0を指定して即時killを選択できる。

### 12.3 Windows backend boundary

初期実装はUnixのみでよいが、Process interfaceは以下を仮定してはならない。

- Unix signal値
- file descriptor
- process group ID
- POSIX exit status

Windows backendではConPTYとJob Objectを利用し、Manager.Close時にprocess treeを回収できる構造を想定する。

streammuxは安全な既定値を提供し、application側で上書き可能にする。

| MaxFrameBytes | 4 MiB |
| PTY ReadBufferBytes | 32 KiB |
| MaxSessions | 256 |
| HistoryBytes | 16 MiB / Session |
| MaxTotalHistoryBytes | 512 MiB / Manager |
| AttachmentQueueBytes | 4 MiB / Attachment |
| ObserverQueueBytes | 4 MiB / Subscription |
| MaxObservers | 32 / Manager |

## 14. Versioningと互換性

- 現行frame header layoutはversion 1として維持する。
- framing versionとPTY protocol payload versionを分離する。
- 構造化payloadには独立したschema versionを持たせる。
- unknown optional fieldは無視し、unknown required capabilityは要求を拒否する。
- Peerはapplicationがconnection開始時にhandshakeを実装できる登録点を提供する。
- 将来header拡張が必要な場合はframe versionを上げ、旧decoderが誤解釈せず拒否できること。
- deprecated APIは少なくとも次のminor releaseまで残し、移行先をdocumentationに記載する。

tagged releaseに含まれる既存`pty.Bridge`はdeprecatedな互換adapterとして残してよいが、新規実装の中心にしない。未commitの`pty.Mux`は互換対象とせず、public APIとして固定する前に`pty.Manager` / `pty.Protocol`構成へ置き換える。

---

## 15. Security Boundary

streammux framing自体はauthentication / authorizationを担当しない。

ただし、protocol handlerは利用applicationが以下を実装できるhookを持つ。

- connection確立時のpeer検証
- Open / Attach / Input / Killごとのauthorization
- ProcessSpecのcommand、cwd、environment検査
- Sessionの可視範囲制限

受信payload length、list件数、文字列長、Args / Env要素数には設定可能な上限を適用する。remoteから受け取ったerror文字列やmetadataをlog formatとして直接使用しない。

---

## 16. Observability

外部metrics libraryへの依存は必須にしない。代わりにhookまたはsnapshot APIで以下を取得可能にする。

- active connection / Session / Attachment / Subscription数
- streamごとの送受信bytes / frames
- queue使用bytesとoverflow回数
- history使用bytesと切捨てbytes
- attach / detach理由
- process開始、終了理由、exit code
- protocol errorとbackend error

raw PTY payloadを既定でlogへ出力してはならない。

## 17. Testing Requirements

### 17.1 Core codec / Peer

- partial read / partial write
- concurrent Call / Emit
- CorrelationID重複防止とwraparound
- response、timeout、cancel、connection closeの競合
- handler重複登録とunknown MessageType
- malformed header、oversized payload、invalid flags
- per-stream orderingとcross-stream並行性
- traffic class priorityとstarvation防止
- byte queue上限
- fuzz testとrace test

### 17.2 Manager / Session

- 複数PTYの同時Open / Input / Output / Resize
- childが最初に観測するterminal sizeがProcessSpec.InitialSizeと一致すること
- ProcessSpecのslice ownershipとEnv nil / empty semantics
- Open context cancel後に既存Sessionが影響を受けないこと
- frontend接続終了後もProcessが生存すること
- Manager.Close時に全Processを回収すること
- Kill / Wait / Closeの同時実行と冪等性
- 自然終了、非0 exit、signal終了、I/O failure
- Session IDをManager lifetime中に再利用しないこと

### 17.3 Attach / history

- attachmentなしでも大量outputでchildがblockしないこと
- history上限と古いchunkの削除
- attach中にoutputが発生してもhistory/live間に欠落・逆転がないこと
- detach後もSessionとhistoryが継続すること
- reattachで保持historyとlive outputを受信できること
- slow attachmentだけが切断されること
- 一つのconnectionで20以上のPTYを同時操作できること
- connectionを繰り返し切断・再接続してgoroutine / memory leakがないこと

### 17.4 Platform

- macOS / Linuxの実PTY integration test
- interactive shell、UTF-8、binary bytes、VT sequence
- process group内に孫processがある状態でのManager.Close
- resize境界値
- PTY EOFのOS差異
- `go test -race ./...`、`go vet ./...`、fuzz corpusをCIで継続実行

## 18. Acceptance Criteria

以下をすべて満たした時点で、Ariadneから新APIを採用可能と判断する。

1. 一つのPeer connection上でapplication control messageと複数PTYを同時に扱える。
2. connectionを切断してもPTY processが継続する。
3. 同じSession IDへ再attachし、保持historyの後にlive outputを順序どおり受信できる。
4. frontendが停止してもPTY output pumpは停止しない。
5. slow frontendが他SessionやPTY processをblockしない。
6. Manager.Close後に所有process、PTY handle、goroutineが残らない。
7. Core、PTY、protocol、platform backendの依存境界が循環しない。
8. application固有型やAriadne固有知識がstreammuxへ入っていない。
9. public APIのownership、cancellation、buffer lifetimeがGo documentationに明記されている。
10. unit、integration、race、fuzz testが成功する。

## 19. 実装順序

破壊的変更を局所化するため、以下の順で実装する。

1. Core `Peer`、protocol registry、request correlation、byte制限付きscheduler
2. connection非依存の`pty.Manager`とSession state machine
3. 常設output pump、history、observer
4. Attachmentとslow consumer isolation
5. `pty.Protocol`と新message set
6. Unix process group cleanupと型付きExitStatus
7. legacy `pty.Mux` / `Bridge` compatibility wrapper
8. integration、race、fuzz、leak test
9. public API documentation更新と新version tag

途中段階でも既存framing coreのtestを維持する。未commitの`pty.Mux`をpublic APIとして固定する前に、本書の責務分離を反映する。

## 20. Ariadne側との契約

Ariadneはstreammux新APIに対して以下だけを仮定する。

- daemon lifetimeのManagerがPTYを所有する。
- frontend connectionはPeerとProtocol attachmentだけを所有する。
- StreamIDはManager lifetime中で安定する。
- PTY payloadはraw bytesである。
- connection切断はdetachであり、killではない。
- Manager終了は全PTYの終了と回収を意味する。

Workspace、Window、Pane、stash、Label、Pluginに関する意味付けはAriadne側で行う。これによりstreammuxを他applicationでも再利用可能に保つ。
